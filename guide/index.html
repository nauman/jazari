Folio 02 · Memorandum

Where this came from

This started as an MCP mistake.

Four MCP servers in Ruby and Rails, and the first one was built the way everyone builds their first one: as another REST API. One tool per endpoint.

That surface grows the way an API grows, except an agent has to read all of it before deciding anything. It had to be reconciled — a sprawl of endpoint-shaped tools collapsed down to roughly fifteen, grouped by what someone is actually trying to accomplish.

The lesson is not "fewer tools". It is that MCP is an adapter, not a layer. Business operations, queries and authorization belong in shared services; REST and MCP are both thin skins over them. REST stays resource-oriented. MCP should be a small set of task-oriented tools shaped around an agent's goal.

Which makes MCP feel closer to a standardised RPC — or an old SOAP-style service contract — than to REST. That is fine. What is not fine is letting it quietly become a second service layer with its own copy of the rules.

THE MISTAKE

One tool per endpoint

The MCP surface mirrors the routes file. Every new endpoint is a new tool. The agent reads a catalogue of verbs and has to assemble the intent itself.

“what can I call?”
THE CORRECTION

A few tools per job

The MCP surface mirrors intentions. Tools group around outcomes, and both adapters call the same service — so authorization cannot drift between them.

“what am I trying to do?”

Working this way across four projects changed a different question entirely: why does operational knowledge live permanently inside a repo? Why is deploy.md a file, next to the code, in one repository, when the procedure it describes governs a fleet?

A document cannot be called

A markdown runbook is a fine thing to read and a useless thing to operate. It has no state, no evidence, no revision guard, and no answer to “is anyone doing this right now?” Committing it harder does not fix any of that.

Where it landed, in one line: rituals live in jazari; the vocabulary stays a registry, because a lexicon is not a procedure; and resume becomes subject-scoped by composing resolve against the canon. The host names what a thing is and points at a recipe id. Nothing else crosses the boundary — the gem never learns your fleet, and you never wait on a gem release to fix a step.

Folio 03 · Failure test

The problem

A checklist knows its state.
It knows nothing else.

Four questions an attached checklist cannot answer — and the one that matters most is the one it destroys when you reset it.

Who ran it?× no
What did they see?× no

The usual fix is a checklist attached to a record. That helps, then runs out: some procedures belong to no record at all, and a checklist you reset to run again has just destroyed the evidence it ever ran.

Folio 04 · Register

The mechanism

Four layers

Each answers a question the one above it cannot. Most systems stop at the second.

IRecipeThe canon

How this ritual is done: its ordered checklist and run policy, stored as data. It is operator-editable and digest-versioned, so fixing a step is a write, not a deploy.

“what steps define this ritual?”
IIRunbookOne subject’s override

How this record’s checklist differs from the recipe. It materialises on first edit; reading the default checklist writes nothing.

“which steps differ for THIS one?”
IIIQueueA name you can always call

A stable name for a recipe checklist that belongs to no record. The name remains callable while the recipe stays its single editable home.

“which checklist do I call?”
IVRunOne execution

A snapshot of the resolved checklist, then its actor, item ticks, per-item evidence and outcome. Later recipe edits cannot rewrite what this run used.

“what happened to every step?”

Whole system / one plate

Follow one checklist from canon to proof.

The plate stays fixed while each operational boundary comes into focus. Callers execute the work; Jazari resolves the checklist, snapshots it for the run, and retains each tick and its evidence.

01 / DEFINE

The recipe owns the checklist

Write the ordered steps and run policy as data. The recipe is the digest-versioned canon, editable without shipping code.

02 / ADDRESS

Resolve its current checklist

A runbook may override the steps for one record. A queue gives the recipe checklist a stable name when no record exists.

Folio 05 · Operating routes

Two operating routes

Local tool or embedded library.

Standalone and embedded are peers. Pick the route that matches your machine; both keep the same procedure model and evidence.

Standalone · v0.8.1

A local file. A JSON conversation.

SQLite stores your procedure state. The versioned jazari/v1 interface lets any language call it. Jazari starts when you call it and exits when the work is recorded.

01

1 · Install and discover

With Ruby 3.2+ installed, these commands create a local SQLite database and report the available features. No database server, daemon, or network listener.

gem install jazari -v '~> 0.8.1'
jazari capabilities --database .jazari/jazari.sqlite3
02

2 · Send JSON, receive JSON

This first request works without seeding a recipe. Send a JSON file with --request request.json, or pipe a request through stdin:

printf '%s\n' '{"protocol":"jazari/v1","request_id":"hello","action":"capabilities","arguments":{}}' \
  | jazari call --database .jazari/jazari.sqlite3 --request -

The response identifies SQLite storage and the CLI and MCP stdio transports. Recipe, runbook, run, and evidence operations use the same interface, with revision checks on writes and structured error codes.

Read the JSON schemas and conformance fixtures.

03

3 · Load your procedures or connect an agent

Seed your YAML or JSON recipe files. Existing recipes keep the operator's edits.

jazari recipes seed config/recipes --database .jazari/jazari.sqlite3

To connect an MCP client, configure it to launch this command with an absolute database path. The server exposes one jazari tool and speaks JSON-RPC over stdio.

jazari mcp stdio --database /absolute/path/to/jazari.sqlite3

Runs retain snapshots, actor attribution, and evidence across calls. Your calling application handles authorization and executes the procedure.

Standalone guide

Embedded Ruby & Rails

Inside your application

Seed a procedure. Address it by name. Open a run, work it, attach what you saw.

1 · Seed

# Your content, never the gem's — it ships zero recipes.
Jazari::RecipeRegistry.seed!([
  { id: "backup.verify.v1",
    topic: "Prove a backup by restoring it",
    description: "## Purpose\n\nA green schedule is not a verified backup.",
    run_policy: "once_per_calendar_day",
    checklist: [
      { id: "dump",    text: "Dump to scratch" },
      { id: "restore", text: "Restore into a throwaway database" },
      { id: "counts",  text: "Compare table and row counts" }
    ] }
])
# seed! is create-if-missing — reseeding never overwrites an operator edit.

# YAML/JSON files are seeds; drift is reported, never overwritten.
entries = Jazari::RecipeFiles.load("config/recipes")
Jazari::RecipeRegistry.seed!(entries)
Jazari::RecipeFiles.drift(entries)

2 · Address

# A queue: a stable name for a ritual that belongs to no record.
target = Jazari::QueueTarget.new(
  queue: "backup-verify",
  public_reference: { kind: "queue" },
  recipe_id: "backup.verify.v1"
)

Jazari.resolve(target: target).progress
#=> { done: 0, total: 3, percent: 0 }

# Or attach to a record you own — you authorize first, always.
Jazari::RecordTarget.new(runbookable: site,
  public_reference: { kind: "site", site: site.slug },
  recipe_id: "site.maintenance.v1")

3 · Run it

result = Jazari.open_run(target: target, actor_ref: "agent:nightly")
run    = result[:run]

Jazari.tick(run: run, expected_revision: run.lock_version,
            item_id: "restore", done: true, actor_ref: "agent:nightly")

Jazari.attach_evidence(run: run.reload, expected_revision: run.lock_version,
                       item_id: "counts", kind: "count", value: "4211 rows",
                       actor_ref: "agent:nightly")

Jazari.close_run(run: run.reload, expected_revision: run.lock_version,
                 outcome: "completed")

# Every mutation carries the revision from the read before it.
# Mismatch raises revision_conflict instead of overwriting.

4 · Answer

Jazari.last_run(target: target).outcome
#=> "completed"

# resolve carries it too, so ONE read answers the question:
Jazari.resolve(target: target).last_run
#=> { id: 4412, outcome: "completed", open: false,
#     started_at: 2026-08-10 03:00:04 UTC, finished_at: ... }

Two details easy to get wrong

The index COALESCEs the nullable polymorphic subject — otherwise queue runs are unconstrained entirely, because NULL != NULL.

And the day is UTC via timestamptz, so one nightly ritual cannot land on two different days depending on which region’s machine called it.

A run records who acted

A checkbox can say what is done. A run also says who did it. Pass an opaque actor_ref for a human, agent, or job. Explicit identities win; trusted system jobs may inject a default when a run opens, and later ticks or evidence inherit the run actor when omitted.

# explicit identity for a human or agent
Jazari.open_run(target: target, actor_ref: "user:42")
Jazari.attach_evidence(run: run.reload, expected_revision: run.lock_version,
                       item_id: "restore", kind: "note",
                       value: "verified", actor_ref: "user:42")

# opt-in default for a trusted system job
Jazari.configure { |c| c.actor_ref = -> { "system:nightly-backup" } }
Folio 07 · Bound insert

Fitting it to your machine

Keep your own MCP tool

The MCP layer is optional — the dispatcher is not even loaded unless you ask for it. If you already have a tool, absorb the actions into it and keep your own dispatch, envelope, naming, and permissions.

The descriptors are the single source of truth: the shipped handler validates against the same list, so a published schema and the implemented behaviour cannot drift.

frag = Jazari::Mcp::Actions.schema_fragment

MY_TOOL[:properties][:action][:enum] += frag[:enum]
MY_TOOL[:properties].merge!(frag[:properties])

# then dispatch to Jazari.* yourself

a = Jazari::Mcp::Actions.fetch("reset")
a.effect     #=> :destructive
a.confirm?   #=> true
Folio 08 · Colophon

The name

Why “Jazari”

Ismail al-Jazari (1136–1206) was an engineer at the Artuqid court in Diyarbakır. He built programmable automata — a hand-washing machine that offered you a towel, a clock driven by a water wheel, pumps with the earliest known crankshafts.

That is not why the gem carries his name.

runbook was already taken on RubyGems — by a DSL for executing procedures, last released in 2021. The name is occupied; the project is not one to build on.

He also wrote The Book of Knowledge of Ingenious Mechanical Devices, finished the year he died: fifty machines, each with numbered construction steps and drawings detailed enough that a stranger who had never met him could rebuild the device — including, in his own words, the steps he had gotten wrong first.

Eight hundred years later, people have built working machines from those pages.

A procedure is not lore in someone’s head or prose in a document nobody opens. It is a written, versioned, checkable artefact that somebody else can execute — and prove they executed.

Folio 09 · Certificate

Scope

Not an execution framework

Jazari holds the state of a procedure. It does not SSH anywhere, shell out, or run your commands — execution is served by whatever you already have. What none of them keep is a durable, addressable record of which procedure ran, by whom, and what came back.
